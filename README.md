# Досуг и развлечения — бот для MAX

Бот, который помогает найти, чем заняться в городе. Собирает события с kassir.ru, фильтрует по интересам, бюджету и свободному времени, отдаёт подборку прямо в чате MAX.

Проект делался на хакатоне по треку «Досуг и развлечения». Ниже — что успели, как запускать и что не докрутили.

---

## Что вообще решает

Живешь в Москве (или СПб/Казани/Нижнем/Хабаровске), вечером пятницы хочешь куда-то сходить. Что делаешь? Открываешь афишу, потом kassir, потом ещё пару сайтов, сверяешь цены, время, категории. Или плюёшь и остаёшься дома.

Мы сделали бота, который всё это делает за тебя. Один раз настроил профиль — дальше в один тап получаешь подборку.

А если хочется чего-то конкретного по времени — пишешь «сб 19:00-23:00», и он ищет именно под это окно.

### Для кого

В первую очередь думали про людей 18–35, которые:
- живут в крупных городах;
- ходят на концерты/в театр/в кино хотя бы иногда;
- не хотят ставить ещё одно приложение ради афиши;
- сидят в мессенджерах постоянно.

### Проблема

Если коротко: **информация размазана по сайтам, а сопоставлять её приходится руками**. Время, цена, категория, локация — всё в разных местах. В итоге или тратишь полчаса, или забиваешь.

## Из чего собрано

```
MAX  ─── polling ───►  bot (Python)  ─── HTTP ───►  backend (.NET)  ───►  PostgreSQL
                       │                              │
                       │                              └──► kassir.ru (HTML + JSON-LD)
                       └── prefs.json (локально)
```

Три компонента:

**bot** — Python, `maxapi` + `httpx`. Держит FSM-состояния пользователя (кто на каком шаге), рисует клавиатуры, парсит интервалы типа «сб 19:00-23:00», ходит в backend.

**backend** — ASP.NET Core Web-API. Ходит на kassir.ru, парсит события, фильтрует по цене и дате. Плюс хранит профили пользователей через EF Core.

**PostgreSQL** — таблица `users` хранит базовую инфорцацию о пользователях, ничего хитрого.

Есть отдельная прослойка с `prefs.json` в боте — там лежит лимит цены и лог запросов городов, которых нет в списке. Это временно, см. «Известные ограничения».

## Запуск через Docker

Нужно: Docker 24+ и compose v2.

```bash
git clone https://github.com/romanzhotin/max-hackathon-pebcak.git
cd max-hackathon
cp .env.example .env # нужно заполнить значения переменных окружения!

# пункт 0 - получаем сертификат https
./initialize-https-cert.sh

# пункт 1 - запускаем всё остальное
./run.sh
```



Бот сразу начнёт слушать MAX. Найти его можно по нику (указан в материалах сдачи), жмёшь `/start` и поехали.

Сборка занимает меньше 5 минут — мы специально не тащили лишнего в образы.

`.env.example` в репозитории без рабочих значений. Реальный `.env` в `.gitignore`.

## Что умеет API

### События

`GET /Events/{city}/{eventType}`

`city`: `msk`, `spb`, `nn`, `kzn`, `hbr`
`eventType`: `default`, `koncert`, `teatr`, `shou`, `kino`, `children`, `festivals`, `excursions`, `sport`, `education`

Необязательные query-параметры: `minPrice`, `maxPrice`, `minStartDate`, `maxEndDate`.

Если ничего не передать — вернёт все события. Если передать — отфильтрует.

Пример:
```bash
curl "http://localhost:5215/Events/msk/koncert?minPrice=500&maxPrice=2000" | jq
```

Ответ — массив объектов schema.org `Event`. Внутри есть `name`, `startDate`, `location`, `offers.price`, `offers.url`.

Ошибки:
- 400 — неизвестный город/категория, нет ld+json на странице, битый JSON;
- 500 — что-то сломалось при парсинге.

### Пользователи

`GET /users/{maxId}` — вернуть профиль. 404 если нет.

`POST /users/{maxId}` — создать или обновить.

Тело:
```json
{ "city": "msk", "categories": ["koncert", "teatr"] }
```

`maxId` — это ID пользователя в MAX, парсим в `long`.

Проверить все эндпоинты вручную можно через swagger: https://maxhack.livvyy.ru/swagger/index.html

## Про бота чуть подробнее

### Состояния

`IDLE`, `ONBOARDING_CITY`, `ONBOARDING_CATEGORIES`, `AWAITING_CITY_NAME`, `AWAITING_PRICE`. Живут в памяти процесса — при рестарте бота сбрасываются. Для хакатона сойдёт.

### Callback-префиксы

`city:`, `cat:`, `menu:`, `price:`, `search_cat:`, `s:`, `ts:`. Роутер — `handlers/callbacks.py`, там же маппинг на функции. Если payload неизвестный — пишем в лог и ack-аем, чтобы кнопка не висела.

### Парсинг времени

```
сб 19:00-23:00
пт 18:30-22:00
19:00-23:00          (любой день)
сб 19:00-23:00, вс 10:00-14:00
```

Разделители между окнами: `,`, `;`, `|`, перевод строки. Внутри времени — `:`, `.`, пробел.

### Дедупликация

Одно событие может прийти из нескольких категорий. Склеиваем по URL (приоритетно) или по `lowercase(name) + startDate`. Категории объединяем в `_categories` — потом все показываем в карточке.

### Почему prefs.json, а не БД

Потому что мы торопились. Лимит цены — штука простая, чтобы ради неё поднимать ещё одну таблицу и миграции. В следующей итерации переедет в Postgres.

## Как проверить

1. `docker compose up --build -d`
2. Дождаться, пока `db` станет `healthy`, а `backend` — `Started`
3. Открыть бота в MAX
4. `/start` → Москва → 2-3 категории →
Готово
5. «Найти события» → смотрим карточки
6. «Ещё N» → вторая страница
7. Написать `сб 19:00-23:00` → события в окне
8. «Бюджет» → «до 1000 ₽» → вернуться, поискать снова
9. «Профиль» → проверить, что всё сохранилось
10. `/reset` → вернуться к выбору города

Backend можно потыкать отдельно:

```bash
curl "http://localhost:5215/Events/spb/teatr" | jq
curl "http://localhost:5215/users/13003734" | jq
curl -X POST "http://localhost:5215/users/13003734" \
  -H "Content-Type: application/json" \
  -d '{"city":"spb","categories":["teatr"]}'
```

Ожидаемое поведение в разных ситуациях — в разделе «Что может пойти не так» ниже.

## Что может пойти не так (и что при этом делает бот)

**Backend лежит.** Бот отвечает: «Не могу получить события, попробуй позже.» Состояние не сбрасывается, можно сразу повторить.

**Города нет в списке.** Бот предлагает написать название — сохраняем в `prefs.json` и говорим «передадим разработчикам». Потом предлагаем выбрать ближайший крупный.

**Цена не парсится.** Если в `AWAITING_PRICE` прислали текст без цифр — просим ввести число. Если прислали интервал типа «сб 19:00-23:00» — переключаемся на поиск по времени (это намеренно, многие путали состояния).

**Ничего не нашлось.** «Попробуй другую категорию, поднять лимит или зайти позже.» С кнопкой «В меню».

**maxId не парсится в long.** Backend отдаёт 400. Бот это покажет как обычную ошибку API.

## Что дальше (если бы было время)

Хочется не просто «добавить ещё городов», а понять, куда это может вырасти.

**Ядро, которое не меняется:** логика FSM, сценарий поиска по времени, дедупликация, схема Bot ↔ Backend ↔ БД.

**Что придётся менять при расширении:**

- Список городов — добавить в `allowedCities` (backend) и `CITIES` (bot).
- Список категорий — в `eventRoutes` и `CATEGORIES`.
- Источник — сейчас только kassir.ru. Если добавлять KudaGo или Culture.РФ, нужен новый парсер под их формат. Хорошо бы вынести это за интерфейс.
- Хранилище prefs — на Postgres.
- Каналы — мини-приложение MAX с картой и календарём напрашивается.

**Порядок тиражирования, как мы его видим:**

1. Текущий пилот — 5 городов, 9 категорий, kassir.
2. Ещё 2-3 источника данных, чтобы не зависеть от одного сайта.
3. До 20 городов-миллионников.
4. Мини-приложение MAX (карта, сравнение, календарь).
5. Партнёрства с организаторами — прямая продажа билетов.

**Главный риск масштабирования** — парсер. Любое изменение вёрстки kassir.ru его ломает. Нужен либо мониторинг, либо несколько источников, либо переход на официальные API/фиды, если они есть.

---

## Что мы хотим получить

Не «увеличить MAU на 20%», а конкретно: сократить путь от «хочу куда-то сходить» до «есть 3-5 вариантов» с 20-30 минут до 1-2.

Метрики, за которыми бы следили:

| Что мерим | Сейчас | Хотим |
|---|---|---|
| Время до первой подборки | 20-30 мин | ≤ 2 мин |
| Сайтов надо открыть | 3-5 | 1 (бот) |
| Доля завершивших онбординг | — | ≥ 70% |
| Вернулись в течение недели | — | ≥ 30% |
| Используют поиск по времени | — | ≥ 20% |

Проверять это можно логами бота (этапы онбординга), access-логами backend (частота вызовов `/Events/*`) и — если докрутим счётчики на callbacks — воронкой по состояниям.

## Честно про ограничения

Мы успели не всё. Вот что болит:

1. **Один источник — kassir.ru.** Ломается вёрстка — ломается всё.
2. **Нет кэша.** Каждый поиск — реальный HTTP-запрос к kassir.
3. **`prefs.json` вместо БД.** При переезде контейнера без volume данные о лимитах теряются.
4. **Нет авторизации.** Профиль определяется по `maxId`, который приходит от MAX. Проверить чужой профиль по чужому ID — можно. Для MVP ок, для прода —
нет.
5. **`EnsureCreatedAsync` вместо миграций.** Пойдёт на старте, не пойдёт при изменениях схемы.
6. **Даты-диапазоны.** Фильтруем по `startDate`. Выставки, которые идут месяц, могут отсекаться некорректно.
7. **Города вне списка** — только пишем в лог. Никаких автоматических расширений.
8. **Состояния FSM в памяти.** Рестарт бота — пользователь снова IDLE, онбординг не продолжается.

Ничего из этого не критично для демо, но всё это первым делом чинилось бы в проде.

## Безопасность и данные

- Токены и строки подключения только в `.env`. В коде их нет. `.env` в `.gitignore`.
- `.env.example` — с пустыми значениями.
- SQL-инъекций нет, потому что LINQ через EF Core.
- XSS не страшен, потому что всё уходит в MAX как plain text.
- HTTPS в dev не форсируем (`app.UseHttpsRedirection()` закомментирован), в `launchSettings.json` профиль есть.

Отдельно про данные: **интеграция с kassir.ru реальная, не мок.** Пользовательские данные — тоже реальные (то, что человек сам ввёл). Моков у нас нет, но есть тестовый набор в `prefs.json` для двух ID — чтобы можно было быстро проверить логику лимитов без ручного прохождения онбординга.

## Что может пойти не так на масштабе

| Риск | Насколько страшно | Что делать |
|---|---|---|
| Поменяется вёрстка kassir | средне | вынести парсер за интерфейс, повесить мониторинг |
| Рейт-лимит от kassir | низко | сейчас `Semaphore(3)`, дальше — backoff и уважение к robots.txt |
| Упадёт Postgres | низко | healthcheck + `restart: unless-stopped` в compose |
| Потеряется prefs.json | средне | переехать в БД |
| Таймаут запроса к API | низко | `API_TIMEOUT=20` + понятная ошибка пользователю |

Допущения, на которых строили: у пользователя есть MAX; kassir.ru отдаёт структурированные JSON-LD и это законно парсить в рамках пилота; 5 городов хватает, чтобы показать ценность.

## Немного про собственный API

* API доступно в течение всего периода проверки по адресу https://maxhack.livvyy.ru

* Файл `openapi.json` есть в репозитории. При необходимости его можно получить по адресу https://maxhack.livvyy.ru/openapi/v1.json

* Тестовые данные так же не используются, поскольку информация о событиях в городе берётся напрямую с сайта `kassir.ru`

* Файл `DATA-API.yaml` так же присутствует в репозитории
